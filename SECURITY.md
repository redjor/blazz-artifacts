# Security policy

## Reporting a vulnerability

Please report vulnerabilities privately, through the repository host's private vulnerability reporting
("Report a vulnerability" in the Security tab), not in a public issue. Include the version or commit, the
deployment shape (reverse proxy, Tailscale…), reproduction steps and the impact you observed. You should get
an acknowledgement within a week. Please give a reasonable delay before public disclosure.

## Threat model in short

Blazz Artifacts publishes **untrusted HTML and JavaScript** (often generated by AI) and shares it with people
who are not administrators. The design assumes:

- the **admin origin** is reachable only by the operator (private network, VPN, tailnet, allow-list);
- the **content origin** is public and serves hostile content to anonymous visitors;
- the two origins are **different hostnames**, and the reverse proxy appends the client address to
  `X-Forwarded-For` (the app trusts only the last entry).

### What is protected

- **Artifacts cannot attack the admin or each other.** Every content response carries a CSP `sandbox` without
  `allow-same-origin` (except PDFs, which carry no script context): each page runs in an opaque origin, cannot
  read cookies, storage or other artifacts' responses. The admin UI lives on another origin under a strict CSP.
- **Access control on the content server**: private artifacts and folders answer 404 exactly like missing ones;
  codes and share links are exchanged for signed, expiring grant cookies; files are only reachable through
  HMAC-signed paths valid for one hour. Bumping an artifact's or folder's access epoch (visibility change,
  new code, "Cut all access") invalidates every grant and signed path at once.
- **Admin authentication**: scrypt password hash, `__Host-` session cookie (HttpOnly, Secure, SameSite=Strict),
  CSRF token and `Origin` check on mutations, rate-limited sign-in and token attempts, optional high-entropy
  API token (stored as SHA-256 only).
- **Secrets at rest**: share-link tokens are stored hashed (lookup) and encrypted with AES-256-GCM (so the admin
  can copy them again); a database leak alone yields no usable link. All keys derive from `HUB_SECRET` (HKDF).
- **Uploads**: streamed to disk with size limits; ZIP extraction rejects traversal, absolute paths, symlinks,
  excessive file counts, total size and compression ratio; Markdown is rendered then sanitised.
- **Visitor privacy**: no script in artifacts, no tracking cookie; IPs and User-Agents are never stored or logged.
  Daily visitor fingerprints are HMACs under a key that changes every day and are deleted after two days.

### What is not protected (accepted limits)

- A **signed path already issued** (open tab, copied address bar URL) keeps working for up to one hour after a
  link revocation or a removal from a folder. "Cut all access" invalidates them immediately.
- Revoking access does not revoke **active share links**: their holders can open them again until you revoke them.
- With `code` visibility, anyone can keep an artifact locked out for others by sending about 20 wrong codes per hour
  (the global lockout that protects against guessing).
- **Simulated browser storage** keeps data in `window.name`, readable by any page opened later in the same tab.
  Do not enable it for sensitive data.
- Admin sessions survive a password change until they expire (7 days); clear `admin_sessions` to force sign-out.
- Rate limiters are in memory and reset on restart.
- The app does not protect against a compromised host, a malicious reverse proxy, or an exposed admin origin with a
  weak password.
